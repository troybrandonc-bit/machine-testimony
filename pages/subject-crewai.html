A count is requirements fully met out of those that apply. This system is assessed as stores, derives, acts, and requirements outside that are not counted against it.

CrewAI has a real gate and a real consolidation step, and both are worth understanding before deploying it where a record matters. The gate is the before_tool_call hook: developer code, filtered by tool name, that can block a call, which satisfies the requirement that risk not be decided by the model. What it does with a block is the problem. HookAborted carries a reason, run_before_tool_call_hooks discards it, and the executor substitutes the fixed string 'Tool execution blocked by hook', which goes back to the model as an ordinary tool result. The refusal survives as narration in a transcript rather than as a decision anybody can query. On the memory side, an LLM emits a keep/update/delete plan over existing records and updates overwrite content in place while preserving the record id and created_at, with no history kept anywhere. Both behaviours are reasonable for a framework optimising for agents that work; neither leaves a record.

Every verdict, and what it rests on

Twenty requirements, each stated as a capability rather than a format, so a system that holds the information in its own shape counts as having it. An absent verdict cites where the assessor looked and did not find it, which is the difference between a measurement and an accusation.

TR-1 Recorded

The record exists and is append-only.

R1.1 · present. When the system stores a fact, does it durably record when that happened?

  • source lib/crewai/src/crewai/memory/types.py:46
    MemoryRecord.created_at is a required datetime on the record itself
  • source lib/crewai/src/crewai/memory/storage/lancedb_storage.py:255
    created_at is serialised into the stored row, so it survives the process

R1.2 · absent. When a stored fact changes, is the previous version still readable?

Once a record is updated, what it previously said is gone. Preserving created_at while replacing content is worse than either alternative for a reader: the record looks as old as the original claim while carrying the new one.

  • source lib/crewai/src/crewai/memory/storage/lancedb_storage.py:320
    "Update a record by ID. Preserves created_at, updates last_accessed." The content field is replaced and the prior value is not written anywhere
  • searched grep -rniE 'def history|version|previous_value|old_value|supersed' lib/crewai/src/crewai/memory/ --include=*.py
    the only matches concern LanceDB table versions and optimistic concurrency retries; there is no memory history table, no version column and no revision chain

R1.3 · absent. Does the ordinary write path ever destroy what was previously recorded?

  • source lib/crewai/src/crewai/memory/encoding_flow.py:457-473
    the encoding flow builds a replacement MemoryRecord reusing the existing id and created_at, and calls self._storage.update(updated). This is the ordinary write path, not an administrative one
  • source lib/crewai/src/crewai/memory/encoding_flow.py:455
    dedup_deletes are applied and counted in records_deleted, so the same path also destroys records outright
  • searched grep -rniE 'def history|previous_value|old_value|supersed' lib/crewai/src/crewai/memory/ --include=*.py
    no match; nothing retains what was overwritten or deleted

R1.4 · partial. Are entries distinguishable by kind, or is everything one undifferentiated blob of text?

There is more than one kind of record in the system, but within memory a claim and whatever produced it are the same shape, distinguished only by whatever a caller happened to put in the metadata dict.

  • source lib/crewai/src/crewai/memory/types.py:20 MemoryRecord
    one record class carrying content, scope, categories, an arbitrary metadata dict, importance and source
  • source lib/crewai/src/crewai/memory/storage/kickoff_task_outputs_storage.py
    task outputs are a separate store, so not everything is one shape

R1.5 · absent. When data must be destroyed for a legal reason, is the destruction itself recorded?

  • source lib/crewai/src/crewai/memory/storage/lancedb_storage.py:440-456
    deletion is expressed as SQL-style conditions such as created_at < timestamp, applied directly to the table
  • searched grep -rniE 'tombstone|deleted_at|erasure|audit' lib/crewai/src/crewai/memory/ --include=*.py
    no match; nothing survives a deletion to record that one occurred

TR-2 Explained

Every belief resolves to its evidence, and disagreements survive.

R2.1 · partial. Can the source a stored fact came from be recovered from the store, by following a link rather than by guessing?

A user id or a session id narrows the origin to a person or a conversation. It does not identify the message, document or event the claim came from, so recovering that means searching the session by hand if it still exists.

  • source lib/crewai/src/crewai/memory/types.py:60-66
    source is "Origin of this memory (e.g. user ID, session ID). Used for provenance tracking and privacy filtering"

R2.2 · partial. Can a fact the system inferred be told apart from one it was told?

The metadata is labelled and the content is not, which is the wrong way round for this purpose. After consolidation a record can hold model-written text while presenting as the original observation.

  • source lib/crewai/src/crewai/memory/analyze.py:18-19
    ExtractedMetadata is documented as "Fixed schema for LLM-extracted metadata", so metadata the model produced is labelled as such
  • source lib/crewai/src/crewai/memory/types.py:20-46
    MemoryRecord.content carries no marker distinguishing text the system was given from text it wrote
  • source lib/crewai/src/crewai/memory/encoding_flow.py:457-473
    a consolidated record's content is new_content written by the LLM, stored under the original record's id and created_at with nothing recording that it was rewritten

R2.3 · partial. When two stored facts about the same proposition disagree, do both survive?

Two disagreeing memories both persist until the consolidation step runs over them, at which point the plan may delete one or overwrite it. This is the textbook case for a partial: survival is real but conditional on a step that runs automatically.

  • source lib/crewai/src/crewai/memory/analyze.py:124-136 ConsolidationPlan
    "LLM output for consolidating new content with existing memories", carrying actions over existing records described as keep/update/delete
  • source lib/crewai/src/crewai/memory/encoding_flow.py:122-139 intra_batch_dedup
    near-exact duplicates are dropped before anything is stored, counted as items_dropped_dedup

R2.4 · absent. Is the disagreement itself queryable, or must a reader diff rows to notice it?

  • searched grep -rniE 'class Conflict|contradict|conflict' lib/crewai/src/crewai/memory/ --include=*.py
    every match refers to LanceDB optimistic-concurrency commit conflicts, not to disagreement between memories. There is no conflict record, id or query surface

R2.5 · partial. When a conflict is resolved, does the record say who resolved it and by what method?

The reason is computed and then not stored. That is a narrower gap than not having one, and closing it would mean carrying insert_reason onto the updated record rather than discarding it after the branch.

  • source lib/crewai/src/crewai/memory/analyze.py:137-139
    insert_reason exists on the plan, so a reason is modelled at the point the decision is made
  • source lib/crewai/src/crewai/memory/encoding_flow.py:457-473
    the record written back carries content, scope, categories, metadata, importance, created_at, last_accessed and embedding. No reason, no deciding model and no reference to what it replaced are among them

TR-3 Gated

Actions carry a verdict, and approvals carry a name.

R3.1 · partial. Does a consequential action produce a durable entry whether or not it ran?

A stopped attempt does leave a mark, which is why this is not absent. What it leaves is a sentence in the model's context, structurally identical to a tool that ran and returned that text. Nothing an auditor could query separates the two.

  • source lib/crewai/src/crewai/agents/crew_agent_executor.py:984-989
    hook_blocked = run_before_tool_call_hooks(...); when true the executor sets result to "Tool execution blocked by hook. Tool: {func_name}" and that string becomes the tool result
  • searched grep -rniE 'ToolUsageBlocked|blocked' lib/crewai/src/crewai/events/ --include=*.py
    no match; no event type distinguishes a blocked call, so a blocked attempt is not emitted as its own thing

R3.2 · present. Does an action's risk class come from somewhere the proposing model cannot write to?

Coarser than a graded risk class, but the substance holds: which tools are gated is fixed in code the model cannot write.

  • source lib/crewai/src/crewai/hooks/decorators.py:208-249 before_tool_call
    hooks are registered in developer code and filtered by tool name and agent, for example @before_tool_call(tools=["delete_file", "execute_code"])
  • source lib/crewai/src/crewai/hooks/tool_hooks.py:171-189 run_before_tool_call_hooks
    the hook decides, and the model has no way to register, remove or satisfy one from its output

R3.3 · partial. Are refusals recorded as faithfully as permissions?

A refusal is recorded in the same channel as a permission, which is the letter of this requirement, but with no marker that it was a refusal rather than an output.

  • source lib/crewai/src/crewai/agents/crew_agent_executor.py:986-989
    the blocked branch produces a result string handled identically to a successful tool result

R3.4 · absent. Does a refusal record why it was refused?

This is the most fixable finding in this file. The reason is constructed and then thrown away two frames later. Returning it instead of a boolean would give every refusal a machine-readable cause at no design cost.

  • source lib/crewai/src/crewai/hooks/tool_hooks.py:140-149 before_tool_call_reducer
    a False return raises HookAborted(reason="before_tool_call hook returned False"), so a reason exists at the point of refusal
  • source lib/crewai/src/crewai/hooks/tool_hooks.py:181-189
    the HookAborted is caught and converted to a bare True; the reason on the exception is discarded and never returned to the caller
  • source lib/crewai/src/crewai/agents/crew_agent_executor.py:987
    the executor substitutes the fixed string "Tool execution blocked by hook. Tool: {func_name}", which names the tool and not the reason
  • searched grep -rn 'reason' lib/crewai/src/crewai/hooks/tool_hooks.py lib/crewai/src/crewai/agents/crew_agent_executor.py | grep -i 'block\|abort\|hook'
    exactly one hit, the HookAborted construction at tool_hooks.py:149. Nothing downstream reads it, so no reason reaches the record or the model

R3.5 · absent. Does an approval identify a person or a named role holder?

The approval is a line entered at a terminal. Whoever is sitting at that terminal is the approver, and the system records neither the fact nor the identity.

  • source lib/crewai/src/crewai/hooks/llm_hooks.py:117-129 request_human_input
    the signature is request_human_input(prompt, default_message) -> str, documented as pausing console updates, displaying a prompt and waiting for input, and useful for "approval gates"
  • searched grep -rniE 'approver|approved_by|principal' lib/crewai/src/crewai/hooks/ --include=*.py
    no match; the return value is the typed text and nothing identifies who typed it

R3.6 · absent. Does the approver's identity come from the authentication layer rather than from something the model can write?

  • source lib/crewai/src/crewai/hooks/llm_hooks.py:117-121
    input is read from the console with no authentication step of any kind in the path
  • searched grep -rniE 'approver|approved_by|principal' lib/crewai/src/crewai/hooks/ --include=*.py
    no identity is captured, so none can be sourced from an authentication layer

R3.7 · absent. Is the acting agent prevented from approving its own action?

  • source lib/crewai/src/crewai/hooks/decorators.py:224-229
    a hook that returns None permits the call, so a hook of one line approves everything it is registered for without any human being involved
  • searched grep -rniE 'approver|approved_by|principal' lib/crewai/src/crewai/hooks/ --include=*.py
    with no principals modelled anywhere, a proposer and an approver cannot be distinguished even in principle
