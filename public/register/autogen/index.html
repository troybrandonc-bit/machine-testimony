A count is requirements fully met out of those that apply. This system is assessed as stores, acts, and requirements outside that are not counted against it.

AutoGen is assessed as storing and acting but not deriving: its memory holds what a caller puts in it, and any inference is done by the user's agents rather than by the framework. It has the best-modelled approval request in this census. ApprovalRequest carries the code and the full LLM context, and ApprovalResponse requires a reason rather than accepting a bare boolean, which is more than the other frameworks here ask for. Two things stop that translating into a record. The reason reaches the transcript interpolated into an output string on a result carrying exit_code=1, which is the same shape an execution error takes, so a refusal and a crash are indistinguishable to anything reading afterwards. And ApprovalResponse has no approver, so the fact that a person decided is not recorded even though the fact that a decision happened is. On the memory side, the built-in ListMemory is an append-only in-process list whose contents carry no timestamp at all.

Every verdict, and what it rests on

Twenty requirements, each stated as a capability rather than a format, so a system that holds the information in its own shape counts as having it. An absent verdict cites where the assessor looked and did not find it, which is the difference between a measurement and an accusation.

TR-1 Recorded

The record exists and is append-only.

R1.1 · absent. When the system stores a fact, does it durably record when that happened?

A caller can put a timestamp in metadata, but then the caller is recording it, not the system, and nothing obliges or checks it. Reading a MemoryContent back gives no answer to when it was stored.

  • source python/packages/autogen-core/src/autogen_core/memory/_base_memory.py:26-36 MemoryContent
    the fields are content, mime_type and an optional free-form metadata dict. There is no time field of any kind
  • searched grep -rniE 'created_at|timestamp|\bts\b' python/packages/autogen-core/src/autogen_core/memory/ --include=*.py
    no match anywhere in the memory package

R1.2 · partial. When a stored fact changes, is the previous version still readable?

Nothing is overwritten, because nothing can be. What keeps this from a pass is that readable later is bounded by the life of the process: the built-in implementation is a list, and preserving it across a restart is the embedding application's problem.

  • source python/packages/autogen-core/src/autogen_core/memory/_base_memory.py:78-131
    the Memory API is update_context, query, add, clear and close. There is no update or delete-one operation, so a stored item cannot be changed and nothing is lost to a change
  • source python/packages/autogen-core/src/autogen_core/memory/_list_memory.py:22-23
    ListMemory is documented as a "Simple chronological list-based memory implementation" holding its contents in the component config, with no persistence of its own

R1.3 · present. Does the ordinary write path ever destroy what was previously recorded?

The ordinary write path is append-only by omission rather than by design: there is no update operation to misuse. That is still the property the requirement asks for.

  • source python/packages/autogen-core/src/autogen_core/memory/_base_memory.py:114
    add is the only write, and it appends a MemoryContent
  • source python/packages/autogen-core/src/autogen_core/memory/_base_memory.py:125 clear
    the only destructive call empties the whole store and is an explicit operation rather than part of writing

R1.4 · partial. Are entries distinguishable by kind, or is everything one undifferentiated blob of text?

The type discriminates the format of the payload, not the kind of record. A claim, the document it came from and a note about an action are all one MemoryContent differing only in what a caller happened to put in metadata.

  • source python/packages/autogen-core/src/autogen_core/memory/_base_memory.py:26-36
    MemoryContent carries a mime_type, so text, JSON, images and binary are distinguishable
  • source python/packages/autogen-core/src/autogen_core/memory/_base_memory.py:35-36
    everything beyond the content and its MIME type goes into an untyped metadata dict

R1.5 · absent. When data must be destroyed for a legal reason, is the destruction itself recorded?

There is also no way to remove one subject's items short of clearing everything, which makes an erasure request an all-or-nothing operation on the whole memory.

  • source python/packages/autogen-core/src/autogen_core/memory/_base_memory.py:125 clear
    "Clear all entries from memory"; the whole store goes and nothing marks that it did
  • searched grep -rniE 'tombstone|deleted_at|erasure|audit' python/packages/autogen-core/src/autogen_core/memory/ --include=*.py
    no match

TR-2 Explained

Every belief resolves to its evidence, and disagreements survive.

R2.1 · absent. Can the source a stored fact came from be recovered from the store, by following a link rather than by guessing?

  • source python/packages/autogen-core/src/autogen_core/memory/_base_memory.py:26-36
    MemoryContent has no field referring to a message, document or event
  • searched grep -rniE 'source|provenance|origin|message_id' python/packages/autogen-core/src/autogen_core/memory/ --include=*.py
    the only matches are docstrings about cleaning up resources; nothing in the package models where a memory came from

R2.3 · present. When two stored facts about the same proposition disagree, do both survive?

Both survive, which is what this asks. They survive because nothing in the framework is capable of noticing they disagree, which is what the next requirement is for.

  • source python/packages/autogen-core/src/autogen_core/memory/_base_memory.py:78-125
    the API offers no update and no consolidation step, so two items that disagree both remain in the list until the store is cleared
  • source python/packages/autogen-core/src/autogen_core/memory/_list_memory.py:22-23
    the list is chronological and nothing prunes it

R2.4 · absent. Is the disagreement itself queryable, or must a reader diff rows to notice it?

  • searched grep -rniE 'class Conflict|contradict|disagree' python/packages/autogen-core/src/autogen_core/ python/packages/autogen-agentchat/src/ --include=*.py
    the two matches are code comments about type variance and content types; there is no conflict record, id or query surface

R2.5 · present. When a conflict is resolved, does the record say who resolved it and by what method?

A pass under the specification's own wording, which records resolution only if it happens. This is the conservative outcome, reached because the framework declines to do the thing rather than because it does it carefully.

  • source python/packages/autogen-core/src/autogen_core/memory/_base_memory.py:78-125
    nothing in the memory API resolves anything: there is no update, no merge and no consolidation, so a disagreement is never decided and never silently closed

R2.2 is not assessed here, because this system is not in that business and marking it down for that would be dishonest.

TR-3 Gated

Actions carry a verdict, and approvals carry a name.

R3.1 · partial. Does a consequential action produce a durable entry whether or not it ran?

The attempt is recorded and the record is well populated. Whether it outlives the run is not the framework's decision.

  • source python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py:69-73 ApprovalRequest
    the request carries the code to be executed and the full LLM message context, so what was proposed is captured in detail
  • source python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py:711-714
    a denied execution returns a result rather than vanishing, so the attempt leaves a trace in the conversation
  • searched grep -rniE 'tombstone|deleted_at|erasure|audit' python/packages/autogen-core/src/autogen_core/memory/ --include=*.py
    no durable record type exists; the trace is a message in the team's history, persisted only if the embedding application saves that state

R3.2 · present. Does an action's risk class come from somewhere the proposing model cannot write to?

Scoped to code execution rather than to tool calls in general, which is narrower than the requirement imagines but is genuinely outside model control within that scope.

  • source python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py:140-141
    approval_func is supplied when constructing the CodeExecutorAgent and is "called before each code execution to get approval"; the model cannot install, remove or satisfy it
  • source python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py:84-86
    the function types are fixed in the framework, so the gate's shape is not something a plan can negotiate

R3.3 · partial. Are refusals recorded as faithfully as permissions?

The refusal is recorded in the same channel and with the same standing as a permission, which satisfies the letter. Structurally it is indistinguishable from a crash: anyone counting failed executions afterwards will count refusals among them.

  • source python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py:711-714
    a refusal returns exit_code=1 with output "Code execution was not approved. Reason: ...", which is the same result type and the same exit code an execution error produces

R3.4 · partial. Does a refusal record why it was refused?

Requiring the reason at the point of decision is better than every other framework assessed here, two of which discard it or never model it. What is lost is the structure: a reason parsed back out of a formatted sentence is not a machine-readable field.

  • source python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py:76-80 ApprovalResponse
    reason is a required str, not an optional one, so a refusal cannot be expressed without giving a reason
  • source python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py:714
    the reason reaches the record interpolated into an output string; the ApprovalResponse object itself is not retained

R3.5 · absent. Does an approval identify a person or a named role holder?

The documented example function reads a console prompt and returns ApprovalResponse(approved=True, reason='Approved by user'). The word user appears in the reason string, which is a sentence rather than an identity.

  • source python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py:76-80
    ApprovalResponse is approved: bool and reason: str. There is no field for who approved
  • searched grep -rn 'approver|approved_by|principal' python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py
    no match; the module that defines the approval surface models no person

R3.6 · absent. Does the approver's identity come from the authentication layer rather than from something the model can write?

  • source python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py:84-86
    an approval function is any callable matching the signature, invoked in-process with no authentication step anywhere in the path
  • searched grep -rn 'approver|approved_by|principal' python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py
    no identity is captured, so none can be sourced from an authentication layer

R3.7 · absent. Is the acting agent prevented from approving its own action?

  • source python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py:84-86
    the approval function is ordinary code in the same process as the agent, so a one-line function returning approved=True satisfies the gate with no person involved and nothing distinguishing that from a human decision
  • searched grep -rn 'approver|approved_by|principal' python/packages/autogen-agentchat/src/autogen_agentchat/agents/_code_executor_agent.py
    with no principals modelled, a proposer and an approver cannot be told apart
